# Experimental: DDL replication over the migration stream

## Narrative

The basic migration implementation copies the schema once at start using `pg_dump` and never again. As a result, a DDL
change on the source after streaming begins is not reflected on the target, so the schemas drift and, worse, a data
change that depends on a new column can arrive at the target before the column exists and stall the apply worker.

This prototype closes that gap for the common case by replicating DDL **over the same logical-replication stream as the
data**, so schema changes land on the target at the correct point in the change stream relative to the rows that depend
on them.

The mechanism uses only stock Postgres:

- An event trigger on the source records each table-modifying DDL statement into a logged table `multigres.ddl_log` that
  is also published as part of the tables that are migrated.
- A table trigger on the target replays each arriving statement as the apply worker applies it. Nothing new is deployed;
  no separate stream, slot, or ordering channel is introduced.

As a result, each DDL is logged into the `ddl_log` table, and each DDL is executed inside the transaction where it was
executed on the source side. It will also honor acknowledgement required by the durability rules.

As a result of that, DDL is required to be transactional since non-transactional statements will generate an error when
executed on the target side. There is a filter on the source side that only logs statements that are transactional and
any other statements are ignored. In particular, this means that statements such as `CREATE SUBSCRIPTION`,
`CREATE INDEX CONCURRENTLY`, or `ALTER TABLE ... DETACH PARTITION ... CONCURRENTLY` are not replicated at all.

## Goals and non-goals

### Goals

- Keep the target schema in sync with the source for **table** DDL (`CREATE TABLE`, `ALTER TABLE`) issued after
  streaming begins, without operator intervention.
- Preserve ordering: a replayed DDL statement applies on the target before any later data change that depends on it
  (single stream, commit order).
- Reuse the existing migration publication/subscription — no extra slot, connection, or coordinator phase.
- Self-cleaning: setup and teardown are wired into the coordinator's IMPORT `runSetup`/`teardown`.

### Non-goals

- Production hardening. This is a proof of concept to learn the shape of the problem, not a supported feature.
- Replicating anything beyond table create/alter. Index DDL (`CREATE INDEX`, incl. `CONCURRENTLY`), `DROP` statements,
  and DDL on non-table objects (types, roles, extensions, …) are deliberately not captured (see _Mechanism_ and
  _Limitations_).
- Rewriting DDL for the target (schema/owner remapping, dependency reordering beyond stream order).

> **Note:** §1–§7 describe the original single-migration, IMPORT-only, unscoped prototype. §8 documents the follow-up
> that makes capture **table-scoped**, correct for **multiple concurrent migrations**, and symmetric across the
> **EXPORT** (fail-back) direction. Where they differ, §8 is authoritative.

## 3. Mechanism

The machinery lives in the **`multigres` sidecar schema** — the same superuser-owned schema that already holds
`multigres.migration` and the other shard metadata on the target (created on the source too if absent). On the target
this means `ddl_log` is ordinary WAL-logged data, physically replicated to standbys alongside the rest of the shard
state. New file: `go/services/multipooler/internal/migration/ddlrepl.go`.

### 3.1 Source — capture

Capture on the source side is done using a DDL log table `multigres.ddl_log` and an event trigger
`multigres.capture_ddl()`.

#### Table `multigres.ddl_log`

The DDL log table is defined as:

```sql
CREATE TABLE multigres.ddl_log (
  log_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  schema_name text NOT NULL,
  table_name text NOT NULL,
  ddl_command text NOT NULL
);
```

| Column        | Type     | Description                                                                                                                       |
| ------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `log_id`      | `bigint` | Surrogate key, `GENERATED BY DEFAULT AS IDENTITY` so the apply worker can insert the source's value without an identity conflict. |
| `schema_name` | `text`   | Schema of the table the captured statement targets.                                                                               |
| `table_name`  | `text`   | Table the captured statement targets (every captured command is table DDL).                                                       |
| `ddl_command` | `text`   | The captured statement text (`current_query()`), replayed verbatim on the target.                                                 |

The log is append-only: every successfully executed DDL is added to it. A DDL that fails for any reason is not logged.

The table lives in the existing `multigres` sidecar schema, which the coordinator does not create on the target (it is
created at bootstrap by `createSidecarSchema`); on the external source, where there is no sidecar schema, setup creates
it.

#### Trigger function `multigres.capture_ddl()`

The trigger function is fired on `ddl_command_end` and will insert one row per captured command with the `schema_name`,
`table_name`, and the full query extracted using `current_query()`. It will only capture commands with a `command_tag`
that is either `CREATE TABLE` or `ALTER TABLE`.

The INSERT commits in the **same transaction** as the DDL, making the log row and the schema change atomic. The event
trigger is armed **after** `CREATE PUBLICATION`, so the publication's own creation is not captured.

That allowlist:

- excludes standalone `CREATE INDEX` (including `CREATE INDEX CONCURRENTLY`, which shares the tag and cannot be replayed
  inside the apply transaction), all `DROP` statements (which report nothing on `ddl_command_end`), and DDL on non-table
  objects;
- still matches a `CREATE TABLE` that carries an inline `PRIMARY KEY`/`UNIQUE` (it emits a `CREATE TABLE` row alongside
  the implicit `CREATE INDEX` row), so the whole statement — index and all — is replayed;
- skips the `multigres` schema so the trigger never records its own machinery.

Creating an event trigger requires **superuser** on the source. The demo/on-prem source (`postgres:17`, superuser)
satisfies this; a NOSUPERUSER source (e.g. Supabase `postgres`) cannot use this path as written.

### 3.2 The stream — same publication

`multigres.ddl_log` is added to the migration's publication alongside the data tables, so its INSERTs are decoded and
applied by the **target's logical apply worker in commit order**. The table starts empty, so `copy_data=true` copies
zero rows at tablesync; only post-start DDL streams. This single-stream property is what guarantees correct ordering
relative to data — no separate DDL channel to race against the data.

### 3.3 Target — apply

- A matching `multigres.ddl_log` table (same column names/types — logical replication maps by name).
- `multigres.apply_ddl()`, an `AFTER INSERT` trigger function, runs `EXECUTE NEW.ddl_command`.
- The trigger is `ENABLE ALWAYS` because, by default, triggers do **not** fire for replication-applied changes (they are
  "origin" triggers). Running inside the apply transaction places the replayed DDL at the right position in the stream.

### 3.4 Coordinator wiring

In `runSetup` (IMPORT), after `ApplySchema` and before `CreatePublication`:

1. `target.SetupDDLApply` — create the target `ddl_log` + `ENABLE ALWAYS` apply trigger (before the subscription, so
   tablesync can sync the table).
2. `source.CreateDDLLog` — create the source `ddl_log` + capture function (event trigger not yet armed).
3. `CreatePublication` — now includes `multigres.ddl_log`.
4. `source.EnableDDLCapture` — arm the event trigger (after the publication).

`teardown` (IMPORT), after the subscription/publication are gone, drops **only our own objects** — the source event
trigger and capture function and `multigres.ddl_log`; the target apply trigger (with the table), apply function, and
`multigres.ddl_log`. It does **not** drop the `multigres` schema itself, since on the target that schema also holds
`multigres.migration` and the rest of the shard metadata. Dropping the source event trigger matters: otherwise the
source keeps logging DDL after the migration ends.

## 4. Limitations

- **Superuser source only** — event-trigger creation requires it.
- **Table create/alter only** — only `CREATE TABLE` and `ALTER TABLE` are captured. Index DDL (`CREATE INDEX`, incl.
  `CONCURRENTLY`), `DROP` statements, and non-table DDL are not replicated, so those changes drift on the target.
- **Unscoped to the migrated table set** — captured statements are replayed verbatim and are not restricted to the
  migration's tables, so an `ALTER TABLE` referencing an object the target does not have will error in the apply worker
  and **stall the subscription**. During a migration, keep source DDL scoped to migrated tables. (A rare
  non-transactional `ALTER TABLE`, e.g. `DETACH PARTITION CONCURRENTLY`, would also fail on replay.)
- **`current_query()` is the whole submitted statement** — a DDL issued inside a function/`DO` block records the outer
  call; a multi-statement submission records the batch. `EXECUTE` replays the recorded text as-is.
- **IMPORT only** — not wired into the EXPORT/reverse path.
- **No conflict handling** — if the target schema has already drifted from the source, replay may fail.

## 5. Follow-ups (if this graduates from experiment)

- **Scope capture to the migrated table set** — filter `pg_event_trigger_ddl_commands()` by the migration's tables (and
  dependent objects) so DDL on unrelated tables cannot stall the stream. (The command-tag allowlist is a first cut; this
  is the object-level cut.)
- **Broaden the command allowlist safely** — support `DROP TABLE` (via the `sql_drop` event and
  `pg_event_trigger_dropped_objects()`) and index DDL, applying non-transactional forms (`CREATE INDEX CONCURRENTLY`)
  out-of-band rather than in the apply transaction.
- **NOSUPERUSER source path** — event triggers need superuser; investigate whether a sanctioned replication/admin role
  can own the trigger, or capture DDL another way, so Supabase-style sources are supported.
- **Skip/allow lists and a gate flag** — make capture opt-in and configurable per migration.
- **EXPORT direction** — mirror capture/apply for the reverse stream.
- **Structured capture** — record the parsed command set (`pg_event_trigger_ddl_commands()`), not just
  `current_query()`, to enable target-side rewriting (schema/owner remap) and per-command filtering of mixed batches.

## 6. Validation

Validated against two real Postgres 18 instances joined by one subscription (source `multigres.ddl_log` in the
publication, target `ENABLE ALWAYS` apply trigger):

- An `ALTER TABLE … ADD COLUMN` and a `CREATE TABLE … (id int PRIMARY KEY, …)` issued on the source after streaming
  began both replayed on the target — the new table arrived with its inline PK index.
- **Ordering proof:** an `UPDATE` that writes the newly added column landed correctly on the target (`note='after-ddl'`)
  — only possible because the `ALTER` was applied first, in stream order.
- Data changes flowed normally alongside (`balance` update replicated).
- A `CREATE INDEX` issued on the source was **not** captured — the index is absent on the target — confirming the
  table-modification allowlist.
- The source `multigres.ddl_log` contained exactly the `ALTER TABLE` and `CREATE TABLE` statements — not the
  `CREATE INDEX`, not the `multigres` machinery, and not `CREATE PUBLICATION` (armed after the publication).

## 8. Follow-up: table-scoped, multi-migration, and EXPORT-aware capture

The prototype in §1–§7 installs **one** database-wide event trigger whose capture function logs **every**
`CREATE TABLE`/`ALTER TABLE` (outside the `multigres` schema), adds a single unfiltered `multigres.ddl_log` to the
publication, and is wired into the IMPORT path only. Three problems follow: (a) DDL on tables that are **not** in the
migration is captured and replayed on the target (creating unrelated tables, or WARN/skip on unrelated `ALTER`s); (b) a
single shared, unscoped log/trigger cannot separate **concurrent** migrations; (c) it assumes IMPORT and does not follow
the publisher across an **EXPORT** switch.

This section describes the follow-up that fixes all three. The feature stays experimental and ungated.

### 8.1 Table-scoping by membership fan-out

Capture is scoped to each migration's own tables via a publisher-side membership table:

- `multigres.ddl_capture_tables (migration_id text, schema_name text, table_name text, PRIMARY KEY (migration_id, schema_name, table_name))`
  records which tables belong to which currently-**publishing** migration.
- The shared `multigres.capture_ddl()` **joins** each command's target table against `ddl_capture_tables` and inserts
  **one `ddl_log` row per matching migration**, tagged with that `migration_id`:

  ```sql
  INSERT INTO multigres.ddl_log (migration_id, schema_name, table_name, ddl_command)
  SELECT m.migration_id, c.schema_name, cl.relname, current_query()
  FROM pg_event_trigger_ddl_commands() c
  JOIN pg_class cl ON cl.oid = c.objid
  JOIN multigres.ddl_capture_tables m
    ON m.schema_name = c.schema_name AND m.table_name = cl.relname
  WHERE c.command_tag IN ('CREATE TABLE', 'ALTER TABLE');
  ```

  A table in migration A only rides A; a table in both A and B produces two rows and rides both; a table in neither
  produces no row and is not replicated.

**Why a publisher-local membership table and not `multigres.migration_tables` directly?** Two reasons. First, an
external source (the IMPORT publisher) has no `migration_tables` sidecar at all. Second, on the Multigres side
`migration_tables` lists **all** migrations, including ones where this side is the **subscriber** (IMPORT) — but capture
must fire only for migrations currently **publishing from this side**. `ddl_capture_tables` holds exactly the
currently-publishing set on this server and is populated from the migration's resolved table set (the same data as
`migration_tables`) at capture setup. It doubles as the refcount for the shared trigger (see §8.3).

### 8.2 Multiple concurrent migrations

The design keeps **one** shared event trigger + capture function per server and separates migrations by tag + row
filter, rather than per-migration triggers/logs:

- **Shared `multigres.ddl_log`**, now
  `(migration_id text, log_id bigint GENERATED BY DEFAULT AS IDENTITY, schema_name, table_name, ddl_command, PRIMARY KEY (migration_id, log_id))`.
  The composite PK matters: two different publishers generate `log_id`s independently starting at 1, and both replicate
  into one subscriber's **shared** `ddl_log`; keying on `(migration_id, log_id)` keeps their rows distinct instead of
  colliding on a bare `log_id`.
- **Publication row filter (PG15+).** Each migration's publication adds
  `multigres.ddl_log WHERE (migration_id = '<id>')`, so only that migration's DDL rows flow on its own subscription even
  though the log is shared. Multigres targets PG17+, so no version guard is needed. `migration_id` is part of the
  replica identity (the PK), which satisfies the row-filter column requirement.
- **Refcounted trigger.** The single `mg_capture_ddl` event trigger is created once (existence-checked, since
  `CREATE EVENT TRIGGER` has no `IF NOT EXISTS`, and a blind `DROP`+`CREATE` would momentarily disarm capture for other
  active migrations). Teardown of one migration only removes its `ddl_capture_tables` rows; the trigger (and the rest of
  the shared capture objects) is dropped only once **no** migration's tables remain registered.

**Alternatives considered.** Per-migration `ddl_log`/trigger tables were rejected: PostgreSQL event triggers are
database-global (not per-table), so N migrations would still need N event triggers all firing on every DDL, each
filtering for its own tables — more objects, more per-DDL overhead, and awkward refcounting, for no isolation benefit
over the single-trigger + row-filter design. The shared-log-with-`migration_id` approach is the cleanest.

### 8.3 EXPORT / fail-back symmetry

Capture must run on whichever side is the current **publisher** (the external source in IMPORT; the Multigres target in
EXPORT) and apply on the current **subscriber**. To install capture/apply on either side, the setup/teardown helpers
take a small `ddlConn` interface implemented by both `source` (external, pgx) and `target` (local admin pool).
`SetMigrationDirection`'s `switchTo` tears down the old-direction roles and sets up the new ones on the correct sides,
then recreates the link; `teardown` handles both directions.

**Dual-role server correctness.** A single Multigres server can host several migrations in mixed directions — a
**subscriber** for IMPORT migrations and a **publisher** for EXPORT migrations at once — sharing one `ddl_log`. The
apply trigger is `ENABLE ALWAYS`, so it also fires on the publisher's **own** locally captured rows (which exist only to
be replicated **out**), which would wrongly re-execute that DDL locally. To prevent this, `apply_ddl` is **guarded** by
a subscriber-side refcount table `multigres.ddl_apply (migration_id text PRIMARY KEY)`: it replays a row only when the
row's migration is registered there (i.e. this server is that migration's subscriber). Locally captured rows for an
EXPORT migration are not in this server's `ddl_apply`, so they are skipped. `ddl_apply` also refcounts the shared apply
objects; `ddl_log` is dropped only when a side is neither subscribing nor publishing.

### 8.4 Decisions (edge cases)

- **Brand-new `CREATE TABLE`** for a table not in any migration's set is **not** replicated — it has no
  `ddl_capture_tables` membership, so `capture_ddl` skips it. `ALTER TABLE` maps to an existing member cleanly. Opting a
  new table into a migration is left out of scope (it would need an explicit membership insert **and** adding the table
  to the publication).
- **`DROP` is still not captured** — it reports nothing via `pg_event_trigger_ddl_commands()` on `ddl_command_end`.
  Unchanged from the prototype.
- **`current_query()` is the whole submitted statement** — a multi-statement batch that touches a migrated table replays
  the entire batch on the subscriber (potentially over-applying the other statements). Noted, not fixed; per-command
  capture is a future improvement.
- **Target-side hardening preserved** — `apply_ddl` still `SET LOCAL search_path` to the captured row's schema (so
  unqualified names resolve as on the publisher) and wraps `EXECUTE` in an exception handler that `WARN`s and **skips**
  a failing statement rather than stalling the stream.

### 8.5 Object lifecycle summary

| Object                                           | Side                   | Scope                       | Dropped when                                   |
| ------------------------------------------------ | ---------------------- | --------------------------- | ---------------------------------------------- |
| `ddl_log`                                        | publisher & subscriber | shared                      | the side is neither publishing nor subscribing |
| `ddl_capture_tables`                             | publisher              | shared (rows per migration) | no migration publishes from this side          |
| `capture_ddl()` + `mg_capture_ddl` event trigger | publisher              | shared                      | no migration publishes from this side          |
| `ddl_apply`                                      | subscriber             | shared (rows per migration) | no migration subscribes on this side           |
| `apply_ddl()` + `mg_apply_ddl` trigger           | subscriber             | shared                      | no migration subscribes on this side           |
